# 全剧高相关广告

用户已从 `novvy_list_products` 全量 Markdown 游戏列表中选定游戏，且独立视频分析 agent 已返回覆盖整剧的结果后，使用本参考文件。单集或片段不能生成广告方案。生成推荐表、创意方案、视频提示词或二次修改前，必须同时读取 `narrative-dialogue-prompt-reference.md`，先固定主/辅助欲望、叙事模型、入场承诺、加速器、角色对白关系、唯一核心玩法动词、阶段成功、因果升级钩子和单一 CTR。`product_icon` 已从参考图组删除：产品 icon 不作为 GPT-image-2、参考图组、上传平台或最终视频模型输入；若产品对象包含 `iconUrl`，只视为平台元信息，不做必填、不上传、不传给后续生成模型。视频解析结果必须包含画风与逐图分类，用来决定 `imageUrls`、`humanImageUrls` 或二者并存的混合上传。

## 策略

使用全剧证据驱动的玩法改编：先识别贯穿整剧的主题与核心冲突、人物/关系弧、世界规则、反复行动、视觉母题和情绪回报，再让游戏的一个真实核心动作继续解决同一种问题、兑现同一种欲望。广告必须让观众认出“这是这部剧的世界、人物和矛盾”，同时清楚理解点击后实际要做什么。

每个候选必须选择且只选择一种主创意依据：

- `剧情点`：依据剧中的具体情节、人物行动、关系变化、反复冲突或代表性场景生成；全剧证据负责证明该点不是孤立关键词。
- `剧尾`：依据尾帧状态、最后对白、残留情绪和未完成钩子生成，让玩法成为结尾之后自然发生的下一步。可靠证据缺失时明确标为未知，不得虚构。

剧尾可以成为方案的主要创意依据，但仍必须服从全剧人物、关系和世界规则，不能只靠同题材、同道具或一句脱离上下文的台词。首次四个候选中至少各有一个剧情点方案和剧尾方案。

例子：

- 餐厅经营剧情：突出经营品类扩容、DIY 装修、快速赚钱循环、员工解锁、菜单升级和收入增长反馈。
- 家装或家庭冲突剧情：突出翻新、装饰自由、前后对比爽感、房间解锁和角色生活改善。
- 解谜或悬疑剧情：突出线索查找、反转揭示、关卡推进和“你能解开吗”的挑战感。
- 生存或资源匮乏剧情：突出资源管理、建造庇护所、风险收益选择和升级循环。
- 恋爱或关系剧情：突出剧情选择、造型、礼物系统、关系修复和情绪回报。

## 匹配规则

按证据评分，不按偏好猜测：

- 全剧主题/冲突匹配：产品核心动作能延续或转化整剧反复出现的主要问题，而不是只共享题材标签。
- 人物/关系匹配：广告保留主要角色的目标、底线、权力关系和变化方向，不把角色降格为游戏口播工具。
- 世界规则与反复行动匹配：玩法输入、反馈和升级遵守剧中已经建立的因果、能力边界或行动模式。
- 视觉母题匹配：标志性场景、道具、色彩、构图或动作来自跨集证据，并服务玩法说明而非表面贴皮。
- 产品卖点匹配：产品描述中的可视化卖点能在所选内容时长内被观众理解。
- 受众匹配：剧集观众的情绪、兴趣、地区/语言约束与产品受众假设一致。
- 市场传达匹配：广告能用一句清楚承诺接住商店/落地页，而不是只展示画面。
- 情绪接续：广告延续全剧积累的主要情绪与观看欲望，再把它转成游戏玩法期待。
- 玩法可视化：产品描述里有能在当前逐镜计划内展示清楚的具体功能。
- 用户情绪连续：观众对整剧人物、关系或目标的投入能自然接住产品承诺。
- 转化率实现方式：明确注意力承接、爽点展示、点击理由、下载/试玩理由和 CTA。
- 风险：避免只靠弱关键词、低置信视频证据或产品描述没有支持的卖点。

每个候选至少引用 3 类相互独立的全剧证据，其中必须包含“主题/核心冲突”和“人物/关系弧”，第三类及以上从世界规则、反复行动、视觉母题、标志性资产、跨集情绪回报或观众动机中选择。证据应说明出现在哪些集或如何跨集演进。

优先选择 `description` 明确支撑广告角度的产品。少于 3 个可行匹配时，可以少给选项并说明原因。

## 推荐表

只返回 3-4 个选项。使用紧凑 Markdown 表格，然后直接请用户选择一个或多个编号。用户多选时，后续每个选项作为独立方案并行推进。

必需列：

- `编号`：稳定选项 ID，如 A/B/C/D。
- `创意依据`：只能是“剧情点”或“剧尾”。
- `依据证据`：剧情点方案写明具体剧情与人物行动；剧尾方案写明尾帧状态、最后对白、残留情绪和未完成钩子。
- `产品`：来自 MCP 的产品名。
- `全剧关联证据`：至少 3 类跨集证据，明确主题/冲突、人物/关系弧和第三类广告锚点。
- `广告创意角度`：先用括号紧凑写明主欲望/辅助欲望（可空）、`Mxx`、`Pxx`、`Axx`（可空）和唯一核心玩法动词，再说明广告如何把全剧问题转成玩法体验。
- `玩法卖点`：要强化的具体卖点。
- `受众`：目标观众和动机。
- `市场传达`：一句话承诺或广告口径。
- `情绪承接`：全剧情绪积累如何转成游戏期待。
- `转化实现`：先写说话者→对象、对白功能和内容后段交给观众的具体动作，再写点击/下载/试玩动机和 CTA 方式；默认不让角色看镜头口播下载。
- `剧情到玩法桥梁`：人物目标、关系冲突或世界规则如何自然转成真实玩法动作。
- `可变内容时长与节奏`：根据完成“剧情承接→真实玩法操作→可见反馈→升级钩子”所需信息量，给出建议内容时长范围和简短分镜节奏；不得默认或固定为 12 秒。最终时长由确认后的逐镜时长相加并扣除镜间转场得到，落版时长另计。
- `推荐理由`：一句话说明为什么优先选。
- `风险/需确认`：不确定点、缺失信息或品牌安全风险。

表格后询问用户选择一个或多个编号，或说明要改哪个产品/广告角度。用户选择前，不生成落版图、不上传参考图、不创建最终 MCP payload。

## 选择后

用户选择一个或多个选项后，生成简洁创意方案和参考图组规划。创意方案先用 `narrative-dialogue-prompt-reference.md` 的内部工作稿核对全剧广告锚点、重点集证据、模型组合、核心动词、阶段成功、因果升级、角色对白和单一视觉 CTR；后续落版图和视频提示词沿用同一组决策，除非用户明确改变广告角度。若用户多选，主流程为每个已选编号启动独立 subagent 并行执行后续创意、落版图、参考图组上传和视频提示词准备；每个 subagent 只能处理自己负责的编号，不共享长上下文。

参考图组只聚焦：

- 男主人公和女主人公的正视图、侧视图，以及其在全剧核心关系与代表性场景中的作用。
- 人物身份一致性：脸部、发型、年龄感、体型、服装风格和身份气质必须基于原视频截图保持一致。
- 用户明确选择后生成并审核通过的人物精修图；未选择时仍使用原视频截图。
- 产品呈现：只使用产品名、英文利益点、英文 CTA 和商店/落地页承接表达品牌与转化，不引入产品 icon 作为素材。
- 审核通过的落版图：由 GPT-image-2 先生成并经用户确认后，作为 `final_card` 槽位进入参考图组。
- 广告中需要保持的全剧标志性背景、道具、色彩和玩法视觉符号，用文字写入后续视频提示词，不再用图片模型做九宫格样例图。

参考图组默认方式：

- 数量：5 张独立图片，按槽位顺序传入最终视频 payload，不拼成单张图。
- 来源：视频解析子流程截取或选定的 `male_front`、`male_side`、`female_front`、`female_side`，用户选择后可替换为审核通过的人物精修图，另加审核通过的 `final_card`。
- 方式：默认使用原始截图和审核通过的落版图；只有用户在“人物精修选择”中选“需要”时，才用图片模型基于原始剧中人物帧生成更详细的人物图。
- 上传：本地文件批量 HTTP 直传必须交给独立上传 subagent；父流程必须传入 `SKILL_DIR`，subagent 先运行 `NOVVY_PYTHON_BIN="$("$SKILL_DIR/scripts/novvy_python.sh")"`，再运行 `"$NOVVY_PYTHON_BIN" "$SKILL_DIR/scripts/upload_ai_platform_asset.py"`，用重复的 `--slot SLOT=SOURCE` 显式传入槽位，不得调用 `novvy_upload_asset`，默认不得运行 `scripts/compose_reference_panel.py`。
- 视频引用：普通上传把多张 URL 数组放入 `imageUrls`；真人写实且使用 Seedance 真人上传时把多张 `asset://...` 数组放入 `humanImageUrls`。

如果没有可用男女主人公正/侧视图，不要进入视频生成；若用户已经提供本地视频路径、视频附件或可分析的视频 URL，由视频解析子流程直接抽取/选择关键帧，不需要用户确认。若仍缺失，再让用户提供人物截图或关键帧 URL。若只能找到最接近的替代角度，必须把每个候选帧物化为本地图片并在同一条消息中逐张内嵌展示，图片旁标注槽位、集数/帧号、角度差异和风险，然后等待用户确认；只给语言描述、帧号、路径或上传引用不算展示。缺少产品 icon 不是阻塞项，因为 `product_icon` 不再参与参考图组、上传或生成。

## 人物精修选择与版本链

生成落版图前，主 agent 必须用 Markdown 询问：“是否需要根据剧中人物生成更详细的人物参考图？”固定提供 `1. 否，使用原剧截图` 和 `2. 是，生成并逐张审核`。等待用户回复 `1` 或 `2`；没有明确回复时保持当前状态，不能替用户选择，也不能调用图片生成。

用户选择“否”时，参考图组继续使用原始人物帧，不创建人物图片任务。用户选择“是”时：

- 按最终参考图组实际需要的角色和正/侧视槽位逐张生成，不做九宫格，不把多个角度拼成一张图。
- 每张 V1 都使用 `model: "gpt-image-2"`，实际英文 `prompt` 写清要增强的清晰度、光线、构图和服装细节，同时锁定人物身份、年龄感、五官比例、脸型、发型、体型、肤色、服装和气质；不得美化成另一个人，不得换脸，不得增加人物。
- V1 的 `imageUrls` 必须包含对应剧中人物原始帧；可用同一人物多张原始帧共同锚定身份。没有源帧时不得生成。
- 每张人物图生成前展示英文提示词和中文理由并等待确认；结果出来后用 Markdown 网页跳转链接展示，标记版本号和对应槽位，让用户通过或提出修改。
- 真人写实剧集的人物精修图必须保持真人照片观感。生成后仍需按后文“真人图片硬审核”重新查看实际像素；通过人物身份审核不等于通过真人图审核。

人物图的修改必须走连续图生图版本链：

- 用户修改 Vn 时，先把反馈拆成“必须修改”和“必须保持不变”，生成 V(n+1) 英文编辑提示词并等待确认。
- 调用 `novvy_create_image_generation` 时，`imageUrls[0]` 必须是 Vn 的结果 URL；后续可继续放原始剧中人物帧作为身份锚点。提示词必须声明 edit the first input image，只改用户点名内容并保留未点名区域、构图和人物身份。
- 不得仅复用旧文字提示词从零生成，不得跳过上一版图片，也不得用 V1 直接覆盖已经存在的 V2。每次都以最新一版为编辑基底，形成 V1 → V2 → V3 的链路。
- 上一版 URL 缺失或不可访问时，先用 `novvy_query_generation` 找回；仍无法找回则停止并说明，不能用新任务冒充二次修改。

## GPT-image-2 落版图

生成参考图组前，先展示 GPT-image-2 落版图生成审核。审核内容只包含：

- GPT-image-2 落版图提示词。
- 为什么这样生成：说明该提示词如何服务产品卖点、CTA 可读性、品牌一致性和最后一镜承接。

不要向用户展示完整图片 MCP payload。GPT-image-2 实际 `prompt` 必须用英文，所有落版图可见文字、利益点和 CTA 都必须是英文；中文只用于解释生成理由。用 Markdown 展示待确认提示词、版本和理由，并明确请用户回复“确认生成”或修改意见；只有收到明确确认后才能调用 `novvy_create_image_generation`。查询到结果后展示落版图 URL，并用 Markdown 链接展示为网页跳转，例如 `[落版图 V1 预览](<结果URL>)`；不要把远程结果 URL 放进图片 Markdown 里渲染。后续 `final_card` 槽位可直接使用审核通过的最新版本；只有用户要求本地保存或远程 URL 无法用于后续上传时，才运行 `download_result_asset.py` 保存本地副本。

落版图的修改与人物图使用相同的连续图生图逻辑：用户修改 Vn 时，V(n+1) 的 `imageUrls[0]` 必须传入 Vn 结果 URL，英文提示词必须明确编辑第一张输入图、应用用户修改建议并保持未点名的版式、产品名、利益点、CTA、配色和构图。若落版图使用了已审核人物精修图，可把这些人物图放在后续 `imageUrls` 中作为身份参考，但上一版落版图始终排第一。缺少上一版 URL 时先查询找回，不得从零重画。每次新版提交前都展示修改摘要、保持项、英文编辑提示词和版本号并等待确认；生成后继续复审，直到用户明确通过。只有最新落版图审核通过后，才能进入参考图组批量上传。

## 真人图片硬审核

只在 `visualStyle.renderingType` 为 `live_action_realistic`，或上传/视频失败表明参考类型可能错误时执行。独立参考图审核 subagent 必须按 `reference-image-audit-subagent.md` 查看每张候选图片的实际像素，生成符合 `reference-review.schema.json` 的带 SHA-256 清单；主 agent 不加载图片长上下文，也不能只读路径、文件名、槽位名、提示词或上游标签。

通过标准必须全部满足：画面含清楚可辨的单个目标人物；面部或人体主体有足够像素；整体达到真人实拍或真人照片级写实观感；身份和要求视角可核对；没有明显动漫、插画、卡通、游戏建模、塑料玩偶或蜡像感。人脸过小、严重模糊、遮挡、拼接混杂、主要是 UI/落版/背景，或模型无法确定时一律拒绝。AI 生成人物图不会自动通过，必须复审生成结果。

只有 `reference_workflow.py plan-upload` 输出的通过槽位才能传给上传 subagent，并为每个槽位增加审核计划与 `--confirmed-human-slot SLOT`。任何未显式确认、哈希变化、非真人或不确定图片都不得进入 `humanImageUrls`；`final_card` 永远不能确认成真人槽位。

## 参考图组上传

展示“参考图组上传执行说明”。说明内容包含：

- 参考图组槽位表：`male_front`、`male_side`、`female_front`、`female_side`、`final_card`。
- 每个槽位的来源路径或 URL、可见特征、置信度和替代风险。
- 画风判断和上传模式：全非真人使用普通 asset 上传并写入 `imageUrls`；全真人用 Seedance 真人上传，返回的公网 `https://...` 或 `asset://asset-...` 写入 `humanImageUrls`；真人与落版/UI 等非真人并存时用 `mixed`，分别上传后让最终视频 payload 同时携带两组字段。不确定图片阻塞，不为了上传模式额外等待确认。
- 将交给上传 subagent 的任务规格。
- 将由上传 subagent 执行的 `"$NOVVY_PYTHON_BIN" "$SKILL_DIR/scripts/upload_ai_platform_asset.py"` 参数；一次用 `--slot "slot=<路径或URL>"` 传入全部槽位来源；真人模式还要逐项显示对应的 `--confirmed-human-slot`，只展示模式、模型和文件路径，不展示 token、签名 URL、凭据、`dataUrl` 或 `base64`，这些只能以占位符出现。
- 上传脚本会在 HTTP 上传前校验图片宽度是否在 300-6000px，并对网络、超时、429、`Retry-After`、API `retryable` 和临时 5xx 按错误信息自动限次重试当前远程操作。若最终失败，必须读取结构化 `failedStep`、`safeNextStep`、`retryable`、`attempts` 和 `retrySummary`：能自动修复的输入问题先修复后重跑，认证/权限/缺素材等需要用户动作时停止，禁止不改任何条件就无限重传。

展示执行说明后，不要等待用户确认；先启动独立参考图审核 subagent，获得已校验 `uploadPlanPath`，再读取 `local-upload-subagent.md` 启动上传 subagent。上传命令必须完全来自计划并传 `--review-plan-json`。不要让用户手动补 URL，不调用 `novvy_upload_asset`，不生成九宫格或拼接参考图。单一模式运行 `build-snapshot`，混合模式运行 `build-mixed-snapshot`；主流程只接收快照 ID、参考字段、真实槽位顺序、按槽位排序的本地 `previewItems` 和精简摘要，不接收 token、签名 URL、base64、完整 `assets`、脚本原始输出或 MCP raw。若字段/数组不完整，按 `response_contract`/`ambiguous_commit` 先找回资产，不自动重传。

上传完成后展示 `referenceUrls`、`referenceField` 和槽位映射；不要直接展开签名 URL、完整脚本输出或真实 asset 调试信息。随后读取快照的 `previewItems` 并展示一一对照 UI 槽位表：每行必须包含槽位名、用本地绝对路径实际渲染的槽位图片、上传后引用摘要、可见特征/品牌要点、将写入视频提示词的一致性用途。“来源路径”或“打开链接”不能代替实际图片。让用户确认是否进入视频提示词，或用槽位名指定替换。

如果某个槽位不合适：

- 用户用槽位名指出修改方向，例如 `male_side` 或 `final_card`。
- 未点名槽位保持不变。
- 若修改的是生成的人物图或 `final_card`，先回到对应图像版本链，以当前最新图片作为 `imageUrls[0]` 生成下一版；禁止从零重画。
- 重新启动上传 subagent 批量上传替换后的完整参考图组。
- 继续使用新的 `referenceUrls` 和 `referenceField`，不得切回 MCP 上传或单图引用。
- 再次展示 `referenceUrls`、`referenceField` 和槽位图片/提示词一一对照表，让用户确认是否进入视频提示词。

## 逐分镜视频生成

参考图组通过后，不输出“Memory 总结”。先把广告写成 `references/storyboard-prompt.schema.json` 的结构化 JSON，再运行 `scripts/storyboard_prompt_contract.py`。只有编译器可以渲染最终逐分镜任务表、中文审核稿、英文 `prompt` 和 payload；主 agent 和方案制作 subagent 都不得手写最终格式、重排标题或在用户确认后自由翻译。

每个分镜仍对应一个独立视频任务：稳定编号只能是 `shot-01`、`shot-02`、`shot-03`，一次 `novvy_create_video_generation` 只能提交编译结果中的一个 `videoTasks[]`。视频模型固定为 `seedance-2.0-fast`；如果用户要求其他模型，说明当前 plugin 只支持该模型，除非用户取消任务。

默认内部设置：

- `model`: `seedance-2.0-fast`
- `ratio`: `9:16`
- `duration`: 用户未指定时单镜默认 `8`，可按内容或用户要求在 `4-15` 秒内调整
- `resolution`: `720p`
- `generateAudio`: `true`
- 分镜数量：默认不超过 `3`；每镜单独提交，禁止把多个分镜合并进一个任务
- 参考图：全部分镜和后续版本必须复用同一个 `snapshotId`、完整数组和实际 `slotOrder`。普通上传用 `imageUrls`，真人上传用 `humanImageUrls`，混合快照同时使用两者。不要按“男主第 1/2 张、女主第 3/4 张”硬编码；数组位置只能以快照槽位映射为准。
- 最后一个分镜的最后 2-3 秒必须生成落版，包含产品名、英文核心利益点、英文下载/试玩 CTA，以及 App Store/Google Play 或落地页承接信息。落版必须干净可读，不能遮挡人物脸；其他分镜禁止提前展示落版。

结构化 JSON 的每个语义字段都用同一个 `{zh,en}` 对象保存；英文屏幕文字、对白、旁白和落版文案使用明确的 `*En` 字段。编译器从同一份数据生成中文审核稿和英文提交稿，校验英文不含中文、提示词不含真实 URL 或 payload 字段，并计算每镜 `promptSha256`。审核稿的任务元数据可以显示时长、画幅、模型和分辨率；实际英文提示词只描述创作目标，不写 MCP 字段名、模型名、分辨率或真实引用。

调用 `novvy_create_video_generation` 时，每个 payload 的英文 `prompt` 只能承载当前分镜和必要的前后镜衔接；使用 `model: "seedance-2.0-fast"`、`ratio: "9:16"`、该镜审核时长、`resolution: "720p"`、`generateAudio: true`。单一快照只写对应字段；混合快照同时把完整 `imageUrls` 和 `humanImageUrls` 写入每个分镜 payload。数组顺序必须保持各自快照分组的槽位顺序，综合 `slotOrder` 只用于提示词绑定。非末镜也传完整数组，但提示词明确只锁定人物/风格、不展示 `final_card`；末镜才沿用其落版元素。

每镜 `referenceBindings` 必须完整列出当前快照 `slotOrder` 且顺序一致；`referenceSnapshot.previewItems` 也必须按相同顺序保存每个槽位的本地绝对图片路径。编译器在每镜【参考图绑定】表中实际渲染这些图片，主 agent 原样展示，不得删图或退化成纯文字。单镜字段写清视觉动作、镜头运动、玩法卖点、英文屏幕文字、英文音频/对白、起始状态和结束交接。编译器固定注入英文媒体、人物一致性和负面约束；真人写实与卡通画风由结构化 `visualStyle` 决定。

整组任务的叙事链必须体现已选 `M` 的“真实操作 → 阶段成功 → 因果升级 → 交权”，但每个单镜审核稿只写本镜承担的阶段。连续性必须固定前后镜的人物位置、动作方向、景别、机位方向、道具状态、光线色温和声音交接。声音与对白必须沿用说话者、对象、关系、语气和声线。角色默认对剧中关系对象说话，只有原剧已打破第四墙时才看镜头；角色不口播产品名、下载或试玩，最终英文 CTA 只放在最后一个分镜的审核通过视觉落版中。

下方旧版文本块只解释历史字段含义，不得复制、手写或作为最终输出。最终标题、顺序、空值表示、角色/槽位展开方式以 `storyboard_prompt_contract.py` 的实际渲染结果为唯一标准；脚本会固定输出【分镜任务】、【参考图绑定】、【人物与画面一致性】、【前后镜连续性】、【当前分镜脚本】、【声音与对白】、【落版】、【负面约束】。

```text
【分镜任务】
分镜 ID：{shot-01}
版本：{V1}
生成一支 {单镜时长} 秒、{画幅} {画风}短视频。
剧情功能：{当前分镜在完整广告中的单一作用}

【参考图绑定】
1. 人物/场景槽位：逐项使用不可变快照中的实际槽位名与实际顺序，说明身份、视角、服装或场景用途。
2. 非标准角色：使用实际 `lead_front` 等槽位，不得套用固定男女主位置。
3. 落版：普通 `imageUrls` 只在快照确实含 `final_card` 时绑定；Seedance `humanImageUrls` 永不传 `final_card`，末镜从已审核落版计划继承英文文案和构图约束。

【人物一致性硬性要求】
当前分镜女主必须始终是固定参考图快照中的同一个人，并与其他分镜一致。
当前分镜男主必须始终是固定参考图快照中的同一个人，并与其他分镜一致。
不得改变人物五官、发型、体型、肤色、年龄感。
不得新增主要人物，不得多人围观。
镜中反射也必须保持人物正确。

【前后镜连续性】
起始状态：{承接前一镜或所选代表性剧情状态的人物位置、动作、景别、镜头方向、道具、光线和声音状态}
结束交接：{交给下一镜的人物位置、动作方向、景别、镜头方向、道具、光线和声音状态}

【当前分镜脚本】
{分镜 ID}，0-{单镜时长} 秒
剧情功能：{这一镜承担的真实操作、阶段成功、因果升级或交权阶段}
画面动作：{具体可拍画面和人物动作}
人物对白：{英文短句对白；无对白则写“无对白，保留环境声/音乐情绪”}
运镜：{镜头运动}
转场：{转场方式}
一致性要求：女主/男主必须严格保持参考图身份一致。

【本镜镜头语言】
{用一句话概括当前分镜的运镜节奏及其如何服务目标受众和玩法卖点}

【声音与对白】
对白和旁白必须是英文，短促自然，适合短剧口吻。
BGM 与情绪递进同步，从全剧主要情绪基调逐渐进入玩法爽感高潮；如果生成语音、角色对白或音频提示，全部使用英文，不生成中文语音。

【负面约束】
不要水印，不要换脸，不要改变人物五官，不要肢体畸形，不要多手多脚，不要服装穿模，不要镜中出现错误人物，不要卡通化真人素材，不要突然切换无关场景，不要新增主要人物；不要生成任何中文画面文字或中文语音；只保留广告所需的英文 CTA 和英文落版图文字，不添加无关字幕或无关品牌标识。
```

调用视频生成前停止，用 Markdown 一次展示并确认整组逐分镜任务，说明任务数、每镜 ID/时长、总预计时长和同一快照，并请用户回复“确认生成”或修改意见。用户可见内容必须原样读取编译器 `reviewPath`；不要展示 `compiledPath` 的完整 payload、真实 URL 或 `asset://...`。收到明确确认后直接使用 `compiledPath.videoTasks[]`，不得再次翻译或改写 prompt。

## 分镜复审和二次修改

每个分镜查询到结果后，不要默认结束。分别展示分镜 ID、分镜版本、视频任务 ID、结果 URL 的 Markdown 网页跳转链接、模型、参考图快照摘要、`referenceField`、比例、该镜时长、分辨率、音频设置和简短生成摘要，然后让用户逐镜通过或提出修改；不要在对话中嵌入远程视频。只有全部分镜都通过才进入拼接。

如果当前分镜通过，冻结该镜的任务 ID、版本和结果 URL，继续复审未确认的分镜；不得提前拼接。

如果用户要求修改：

- 只整理被点名分镜的“必须修改”和“必须保持”，按人物动作、镜头节奏、字幕、声音、落版图、CTA 分类。
- 只为该镜新建版本号，例如 `shot-02 V1` 递增到 `shot-02 V2`；其他已通过分镜保持不变，不重新提交，不要声称能直接编辑原任务。
- 默认沿用同一个参考图快照、`referenceField`、人物一致性规则、已通过落版图、品牌安全限制和固定视频参数；只有用户明确要求才调整该镜时长。
- 如果只改该镜画面、节奏、字幕、声音、落版文案或 CTA，继续使用原参考图快照；若改落版图卡面，先回到 GPT-image-2 落版图审核并重新批量上传参考图组，创建新快照后再处理受影响分镜。
- 如果用户要求换人物截图或其他参考图，先回到参考图组上传流程；最终拼接不得混用旧、新参考图快照下的结果。
- 如果用户要求换模型，说明当前 plugin 只支持 `seedance-2.0-fast`，不提供模型切换。
- 修改对应结构化 shot、递增版本，再用 `storyboard_prompt_contract.py --shot-id <ID>` 只编译该镜。原样展示新 `reviewPath`，确认后直接提交新 `videoTasks[0]`；不得自由翻译或手写 payload。
- 新任务完成后只复审该分镜，直到通过。

## 上传或视频失败恢复

任何上传失败或 `novvy_query_generation` 失败都要先写净化后的 `novvy.generation-recovery.v1` JSON，并运行 `scripts/reference_workflow.py plan-recovery`。不要从 stderr 或平台 raw 临场猜测。

- `material_not_human`、`human_review_required`、`reference_mode_mismatch`：启动参考图审核 subagent 重新查看当前实际像素；排除非真人，不确定项阻塞，只把合格真人走 `seedance-human`，再建立新快照。
- 视频阶段建立新快照后，旧快照下所有已提交、已生成、已通过和失败分镜全部标记失效；重新编译整组，列出所有受影响分镜，经用户再次确认后重生成。不得只重生失败镜后与旧快照通过镜混拼。
- `reference_invalid_or_inactive`：先恢复或等待原资产，不直接重传。
- `ambiguous_commit`、`response_contract`：先按平台记录找回已创建资产/任务，避免重复创建。
- `transient_remote`：只重试当前远程操作，最多 3 次，不触发素材重审。
- 认证、权限、参数、内容策略和未知错误停止，执行 `safeNextStep`。

参考图纠错任务创建成功并取得任务 ID 后，立即运行 `reference_workflow.py record-correction`，把新快照、全部受影响分镜和任务 ID 写入同一个 workspace `recovery-state.json`。后续 `plan-recovery` 必须传该 `--state-file`，以持久计数为准。每镜最多允许 1 次参考图纠错重生成；第二次同类失败立即停止。任何新一批付费重生成都必须再次确认任务数和时长。

## 最终视频拼接

全部分镜通过后，在 Novvy workspace 写 `novvy.approved-storyboard.v1` 拼接清单，包含 `activeSnapshotId`，以及按顺序排列的 `shotId`、`order`、`version`、`status: approved`、`snapshotId`、`source`。运行 `scripts/concat_storyboard_videos.py --manifest`；脚本会拒绝未通过、乱序、无结果或混用快照的分镜。远程结果只下载到 Novvy workspace 临时目录，认证信息不会写入输出。

```bash
SKILL_DIR="<novvy-ad-creative skill 根目录>"
NOVVY_PYTHON_BIN="$("$SKILL_DIR/scripts/novvy_python.sh")"
NOVVY_WORKSPACE_DIR="${NOVVY_WORKSPACE_DIR:-$HOME/novvy_ad_workplace}"
"$NOVVY_PYTHON_BIN" "$SKILL_DIR/scripts/concat_storyboard_videos.py" \
  --manifest "$NOVVY_WORKSPACE_DIR/storyboards/<方案ID>-approved.json" \
  --output "$NOVVY_WORKSPACE_DIR/final-videos/<方案ID>-final-v1.mp4"
```

拼接脚本先用 `ffprobe` 校验每个输入包含视频流，再统一为同一尺寸、帧率、H.264、AAC 48kHz 双声道。每个分镜交界固定加入默认 `0.35s` 的 FFmpeg `xfade=fade` 画面交叉淡化，并对对应音轨使用同步 `acrossfade`，避免画面或声音硬切；用户明确要求时可用 `--transition-seconds` 在 `0.1-1.5s` 内调整。无音频分镜会补静音轨，避免音轨错位。因为转场必须重新编码，最终拼接不再使用 concat demuxer 无损直拼。输出固定在 Novvy workspace，默认拒绝覆盖已有文件；明确需要覆盖时才传 `--overwrite`。

成功摘要必须包含 `transition.type: crossfade`、`durationSeconds`、`boundaryCount` 和 `audioCrossfade: true`，便于用户确认最终成片确实应用了转场。

脚本失败时读取结构化 `failedStep` 和 `safeNextStep`：缺文件或结果 URL 不可访问时先找回该镜结果；缺 FFmpeg 时运行环境检查；媒体规格错误时修复输入。拼接失败本身不触发重新提交视频生成任务。成功后展示最终本地 MP4 路径、分镜顺序、总时长、拼接模式 `stream_copy` 或 `normalized`，并保留各分镜任务 ID 与最终文件的映射。
