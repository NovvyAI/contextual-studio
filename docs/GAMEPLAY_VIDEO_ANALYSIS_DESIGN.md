# 真实游戏玩法视频分析 Design

## 目标

在“游戏分析”阶段允许用户上传一段真实游戏玩法视频。系统分析玩法、操作过程和 UI，并将结果用于后续创意、分镜和视频提示词生成。

最终目标：游戏玩法与上传视频一致，同时保留所选短剧的人物、画风和视听语言。

## 最高生成原则

> 玩法真实性是硬约束，短剧画风是视觉约束。改变表现方式，但不改变玩法规则。

系统必须严格还原用户上传的真实游戏玩法，包括操作方式、操作对象、规则、UI 结构、成功反馈和失败反馈；同时使用短剧素材控制人物身份、服装、场景、摄影、光影、表演和整体美术质感。

短剧画风不得改变游戏玩法，游戏原视频的画风也不得覆盖短剧视觉世界。这个功能不是把游戏改编成一种新的“短剧玩法”，而是使用短剧的视听语言准确呈现原游戏玩法。

### 玩法真实性硬约束

真实玩法视频负责约束：

- 玩家执行什么操作；
- 操作对象是什么；
- 对象移动到哪里；
- 游戏目标和规则是什么；
- 操作成功后发生什么；
- 操作失败后发生什么；
- UI、按钮和关卡结构；
- 游戏中不存在、因而禁止模型虚构的内容。

Agent 不得为了增强剧情效果或画面表现而改变以上事实。

### 短剧视觉约束

短剧素材负责约束：

- 人物身份、长相、发型、服装和配饰；
- 场景和时代背景；
- 真人或动画质感；
- 构图、机位、镜头和运镜；
- 灯光、色彩和材质；
- 演员表演和剧情情绪。

例如，真实玩法视频使用卡通界面而短剧使用真人悬疑风格时，可以让短剧中的真人角色在悬疑场景中操作游戏，但游戏操作、规则、UI 结构和反馈逻辑必须保持真实。

## 页面设计

在游戏分析 Tab 提供两种分析入口。

### 游戏商店页面

保留现有功能：

- 输入 Google Play 或 App Store 地址；
- 分析游戏卖点、受众和市场定位。

### 真实玩法视频

新增上传区域：

- 支持拖入或选择 MP4、MOV、WebM；
- 可填写游戏名称；
- 可关联一条已有游戏分析；
- 点击“开始分析玩法”。

页面依次显示以下状态：

- 正在上传；
- 正在提取关键操作；
- 正在理解玩法规则；
- 正在整理玩法证据；
- 分析完成或失败。

## 分析结果

完成后生成一条“玩法视频分析”记录，展示：

- 游戏核心玩法；
- 玩家操作方式；
- 游戏目标；
- 成功反馈；
- 失败反馈；
- UI 布局；
- 真实关卡结构；
- 可用于广告的玩法爽点；
- 禁止编造的玩法；
- 按时间排列的操作过程。

时间证据示例：

```text
00:02–00:04
玩家将红色物品拖入红色容器。

00:04–00:05
容器发光，物品消失，关卡进度增加。
```

系统同时保存：

- 原始玩法视频；
- 玩法关键截图；
- 操作前、操作中和操作后的连续截图；
- 模型输出的结构化分析结果。

## 数据结构

游戏分析记录增加 `gameplayVideoEvidence`：

```json
{
  "gameplayVideoEvidence": {
    "videoId": "gameplay-video-01",
    "coreLoop": "拖动不同颜色物品至对应容器",
    "playerActions": [],
    "successFeedback": [],
    "failureFeedback": [],
    "uiConstraints": [],
    "forbiddenFabrications": [],
    "timelineEvidence": []
  }
}
```

一条游戏记录可以关联多个玩法视频，但需要指定一个“主要玩法参考”。

## 后续工作台使用

进入创意工作台时，用户选择：

- 一条短剧分析；
- 一条游戏分析；
- 可选一段主要玩法视频。

后续阶段读取方式：

- 创意方案：结合真实玩法设计剧游连接；
- 剧情与分镜：游戏镜头必须绑定玩法时间段；
- 分镜图：使用玩法截图约束游戏 UI；
- 视频提示词：自动加入真实操作、反馈和禁止编造项；
- 视频生成：短剧素材控制人物与画风，玩法视频控制游戏机制。

## 提示词编译原则

每个游戏镜头分别包含：

```text
短剧风格约束
真实玩法动作
游戏 UI 约束
成功或失败反馈
玩法视频时间证据
禁止编造内容
使用的图片和视频参考
```

系统不直接把整段玩法分析拼入提示词，而是按镜头选择相关玩法证据。

正式视频提示词必须将玩法硬约束和短剧视觉约束明确分区，不得混写成一段模糊的自然语言：

```text
GAMEPLAY TRUTH — HARD CONSTRAINTS

严格复现玩法参考视频 00:03–00:07：
玩家拖动红色物品进入红色容器。
正确匹配后物品消失，容器发光，顶部进度增加。
不得改成点击、合成、三消或其他玩法。
不得添加参考视频中不存在的按钮和反馈。
```

```text
SHORT-DRAMA VISUAL STYLE

保持已确认短剧人物的身份、服装和造型。
保持宴会厅场景、真人电影质感、冷色悬疑光线和克制表演。
短剧风格只改变视觉表达，不改变游戏操作、UI 结构和反馈逻辑。
```

## 用户确认

在生成正式视频提示词前展示“玩法还原计划”卡片，包含：

- 每个镜头采用哪段玩法；
- 需要还原什么操作；
- 哪些部分保留短剧画风；
- 哪些 UI 和规则不能修改。

用户确认后再生成逐镜视频提示词。

卡片应把信息明确分为“必须严格还原的游戏玩法”和“必须保留的短剧画风”两个区域，并固定显示：

> 玩法内容以真实玩法视频为最高事实来源；短剧素材只控制视觉风格和剧情包装。

## 生成前质量门槛

每个包含游戏操作的镜头都必须通过以下检查：

- 是否绑定了真实玩法视频的具体时间段；
- 玩家操作、对象、目标和结果是否与原视频一致；
- UI、按钮、关卡结构和反馈是否存在虚构；
- 是否保留了已确认的短剧人物与视听风格；
- 短剧风格是否错误地改变了玩法规则；
- 游戏原视频的画风是否错误地覆盖了短剧视觉世界。

任一“玩法真实性”硬门槛未通过时，不允许提交正式视频生成任务。

## 失败和兼容策略

- 没有上传玩法视频时，继续使用现有商店页分析流程；
- 玩法视频与商店页描述冲突时，优先采用真实玩法视频并提示用户；
- 模型无法确认某项规则时，标记为“未验证”，不得写入硬性玩法提示词；
- 上传多个视频时，允许选择主要参考，其他视频作为补充证据；
- 玩法视频默认只用于分析，不自动进入最终视频生成接口；只有模型支持且用户确认时，才作为视频参考输入。

## 实施边界

本设计只定义产品流程和数据契约，暂不改动现有游戏分析、工作台或媒体生成代码。实施时应继续遵守项目本地 Skill 政策，所有运行时依赖的分析与提示词契约必须保存在 `.agents/skills/` 中。
